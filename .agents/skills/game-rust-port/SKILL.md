# ゲームのRust構造対応

原作のルールを動かしたまま、表示・入力・環境依存部分をRustが担当する構造を作る。対象作品の現在の仕様とユーザーの移植範囲を優先する。

## 変更前に構造と原因を調べる

- 適用される `AGENTS.md`、作品のREADME、現在の設計資料、ビルド入口を読む。原作の版・取得元・ソースの識別情報、変更用ソース、実際に起動する生成物を特定する。過去の計画を現在の実装と扱わない。
- 不具合修正では、症状を再現し、物理入力からゲーム本体・表示まで呼出しと状態遷移を追う。入力の二重送信、入力待ちの取り違え、表示キャッシュ、ゲーム本体の状態変化などを切り分け、根本原因の根拠を得てから設計・変更する。
- 新規移植では、原作の開始、コマンド、追加入力、表示、乱数、ターン進行、保存、終了の経路と状態の所有者を調べる。原作を起動できる比較基準を確保し、調査で分かった境界を設計にする。
- ユーザーがゲーム本体のRust化も明示した場合は、その範囲のルール移植と原作比較を計画する。通常のRust対応を、ゲーム本体全体の書き直しへ広げない。

## 状態の所有者と依存を分ける

| 層 | 担当する判断・状態 |
| --- | --- |
| 原作のゲーム本体 | 移動、戦闘、生成、アイテムの効果、ターン、乱数、知識と可視性、勝敗、ゲーム状態の保存 |
| Rust入力 | キーボード・タッチの意図、入力待ちに応じた変換、文字編集、コマンドと後続選択の送信 |
| Rust表示 | 公開済み情報の翻訳と描画、ゲームウインドウ、持ち物の操作候補、地図・HUD・ログ・設定 |
| Rustプラットフォーム | 実行環境への命令、セッションの寿命、保存コンテナの検証、読み込み・書き出しと復元の調整 |
| 接続部分 | C/C++とのFFI、OS・ブラウザーAPI、Workerや描画APIへの薄い接続 |

基本の経路は **Rustのゲームウインドウ・操作部品 → Rust入力 → 原作のゲーム本体 → Rust表示**。OS・ブラウザー固有の処理はプラットフォームの境界に置く。

- 同じ状態を複数の層で独立更新しない。表示へ渡すデータは所有者が公開したsnapshotやdescriptorにし、表示からゲーム内部を書き換えない。
- Rust対応を入口のRustラッパー追加だけで完了としない。表示・入力・環境依存の判断がC/C++やJavaScriptに残っていないか、実際の呼出しとデータの所有者を確認する。
- JavaScriptやOSアダプターはAPI実行・メモリー転送・イベント観測を担当する。ゲームコマンドの意味、モーダルの候補、可視性、保存の妥当性などの判断は担当のRust層へ置く。
- Bevyを使う作品では、Pluginとsystemの順序を入力・ゲーム処理・表示の契約に合わせる。描画フレームや経過時間でターンを進めない。別作品へ同じレンダラーやECSを機械的に強制しない。

## 境界を明示して接続する

- ABIの正本を一つにし、固定幅の値、意味ID、型付き引数、長さ付きのbyte列など、解釈が決まるデータを渡す。借用メモリーの寿命、確保・解放の担当、版、失敗時の扱いを定める。FFIとunsafeは接続部分に限定する。
- 入力待ちは通常コマンド、品物、方向、文字、一覧・ページ送り、確認などに区別する。空キューをEscや仮の入力にせず、実際の待ちが成立してから対応する入力を送る。
- 原作が選択を要求した操作にはゲームウインドウや適切な操作部品を割り当て、選択・取消・完了後の復帰まで接続する。方向指定はその作品の通常方向入力を再利用する。通常画面に不要な一時操作は入力待ちに応じて出す。
- 文言を境界へ出す場合は、可能な限り整形前の意味IDと引数を渡し、Rust表示で言語を解決する。完成した英文の逆解析を意味データの代わりにしない。ユーザー入力の文字列はデータとして保持する。
- 原作が未公開の地形、敵、罠、アイテムの正体や効果を、descriptor・翻訳引数・画像選択などから漏らさない。
- Canvas指定の作品では、可視の画面とゲームウインドウをCanvasへ出す。IME等の補助要素は必要なブラウザーAPIとの接続に限定する。読み上げ等の追加機能を移植に混ぜない。

## 乱数・ターン・保存を保つ

- UIだけの再描画、言語・倍率変更、スクロール、全画面切替でゲーム本体のコマンド・乱数・更新処理を呼ばない。原作コマンド自身が起こす表示や乱数の消費とは区別する。
- 固定シードと同じ消費済み入力で、原作と移植版の状態・乱数・ターン・次の結果を比較する。見た目が同じことや単一の最終結果だけを、乱数不変の根拠にしない。
- ゲーム本体のserializerを保ち、Rust側の保存形式には必要な版・識別情報・整合性検査を持たせる。生ポインターや呼出しスタックを保存データにしない。
- 入力途中の復元が必要なら、現行方式に従ってcheckpointと実際に消費された入力を扱う。送信済みと消費済みを混同せず、保存済みの入力を物理キーとして二重変換しない。
- 新しい実行instanceへロードし、待ちの再構築と次のゲーム操作まで確認する。古いinstanceのcallbackや入力を新しいセッションへ渡さない。

## 実装と確認

原作の取得物を比較元として保持し、変更範囲のライセンス・配布条件を確認する。入力から後続処理・表示まで通る単位で実装し、対象作品の既存ビルドと比較検査を使う。

ブラウザーの動作確認はPlaywrightを使う。変更した操作について、開始だけでなく品物選択・方向・確認・取消・終了後の次操作まで実行する。表示変更はスクリーンショットでも確認する。保存・入力・UIだけの変更では、関連する乱数とターンの不変も確認する。

「全コマンド確認」が依頼範囲なら、原作のコマンド定義と条件付き経路から操作一覧を作り、実行・後続選択・取消・復帰の結果を記録する。未到達・skip・実機未確認を分け、Rust単体検査の成功を実C/C++ゲームの成功へ言い換えない。テスト用fixtureや操作用exportは通常配布へ混ぜない。

完了報告では、変えた境界、保ったゲーム挙動、比較元、実際に実行した検査、Playwrightの結果と未確認範囲を示す。独立レビューを行う場合は、適用される `AGENTS.md` の担当・モデル・推論強度に従う。
