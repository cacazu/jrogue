# Preserved Pascal/Lua core: browser toolchain and ABI gate

**Historical capability audit; the compiler acquisition findings below have been superseded.** The pinned official FPC source now builds a Windows-hosted wasm32 compiler, two WASI RTL configurations and eight package trees. Authored Pascal probes passed in Node WASI, and original Lua C ABI/error/coroutine probes passed in Node and Chrome. Current reproducible evidence is in [FPC-WASM-BUILD.md](FPC-WASM-BUILD.md) and [LUA-WASI-ABI.md](LUA-WASI-ABI.md). The mixed-runtime unified allocator and full original game remain pending; new heavy jobs are temporarily held by the parent to coordinate shared Windows resources. The original sources and narrow compatibility rationale below remain useful input to those checks.

The required gameplay implementation is the original DRL/Valkyrie FreePascal code and original Lua rules. Rust owns display, input and platform adapters. The existing Rust numeric laboratory supplies reference checks only. A viable next investigation is **FPC development WASM + statically linked Lua 5.1.5 C in one core module**, with a narrow command/snapshot ABI to the separate Rust UI module. This is a source-supported candidate, not an already working DRL browser build. Audit date: 2026-10-02.

## Verified compiler support

FPC's [official homepage](https://www.freepascal.org/) identifies stable 3.2.2, development 3.3.x, and WebAssembly support in development. Stable 3.2.2 is a bootstrap candidate, not the desired WASM compiler. Its compiler is GPL; RTL/packages use a modified LGPL allowing static application linking. Preserve the actual downloaded notices rather than applying the compiler license to every output component.

The [official development instructions](https://www.freepascal.org/develop.var) recommend the latest stable compiler to bootstrap development, warn that other starting compilers are not guaranteed, and expose the source repository `https://gitlab.com/freepascal.org/fpc/source.git`. Daily source/binary snapshots are mutable and not guaranteed bug-free. Acquire a specific source commit and record archive hashes and executable self-reported revision.

Current official [target definitions](https://gitlab.com/freepascal.org/fpc/source/-/raw/main/compiler/systems/i_wasi.pas) register **wasm32/wasip1**, wasip1threads and an under-development wasip2. Wasip1 uses little endian memory, a 32-bit pointer target and a default 8 MiB stack. Begin with single-threaded wasip1. Current FPC selection is `-Pwasm32 -Twasip1`; source builds select `CPU_TARGET=wasm32 OS_TARGET=wasip1`. Older tutorials using `wasi` predate the target rename.

Official [WASM calling conventions](https://gitlab.com/freepascal.org/fpc/source/-/raw/main/compiler/wasm32/cpuinfo.pas) include `cdecl` and `stdcall`; this supports investigating Lua's C callbacks without translating gameplay. The [WASI linker implementation](https://gitlab.com/freepascal.org/fpc/source/-/raw/main/compiler/systems/t_wasi.pas) includes both internal and external linking, the latter invoking `wasm-ld`. The source visibly gathers object files; do not assume an unchanged native `{$linklib lua5.1.a}` recipe consumes C archives correctly. Inspect the selected compiler's actual generated link inputs and prove a C-object call before the game build. These source URLs are current development observations, not yet the pinned compiler for the project.

## Concrete Lua/Pascal compatibility work

These findings are from the acquired locked DRL/Valkyrie/Lua sources, which are retained unchanged in `upstream/` and sanitized in `native/`. Compatibility patches belong in a distinct adapted core tree and should not modify the pristine/native baseline.

| Source evidence | Narrow adaptation/probe required |
| --- | --- |
| Valkyrie `libs/vlualibrary.pas` already has a `LUA_STATIC` path: `LuaDefaultPath='lua5.1.a'`, static `cdecl external` symbols and a successful static `LoadLua`. `src/valkyrie.inc` selects static by default off Windows unless dynamic is requested. | Select the static path explicitly. The unit still unconditionally uses `vlibrary`; that unit uses `dynlibs` and native load/unload functions. Guard unused dynamic-loader code/dependencies in the WASI path. Prove actual C object/archive linkage rather than bundling a DLL. |
| `libs/vluatypes.inc` declares `lua_Integer=int64`; Lua 5.1.5 `src/luaconf.h` unconditionally defines `LUA_INTEGER ptrdiff_t`. | On wasm32 C ptrdiff_t is 32-bit: this produces **i64 versus i32 signatures** for APIs such as push/take integer. Align explicitly. A reviewed WASM Lua config using 64-bit integers can preserve the existing Pascal binding's numeric contract; simply adding `-DLUA_INTEGER` is inadequate if the header redefines it. Document/validate numeric range and conversions against original native behavior. |
| Binding `LUAL_BUFFERSIZE=1024`; C `LUAL_BUFFERSIZE=BUFSIZ`. Binding packed `lua_Debug` omits C's `lastlinedefined` member. | Fix configuration/layout in the adapted copies; compare `sizeof`, alignment and every relevant field offset using authored C/Pascal probes, including buffers, debug records and callback records. Do not rely on native permissiveness. |
| Lua callbacks/allocator are `cdecl`; engine stores Pascal userdata and calls back through Lua. WASM has function-table indices and one core linear memory. | Link Pascal and Lua into the same core module and test callback signatures, userdata identity and ownership. Prevent overlapping Pascal/C heaps; a Lua allocator delegating to the core allocator is a candidate requiring proof. Rust/UI memory remains separate; copy serialized bytes through owned buffers. |
| Lua's normal protected-error path uses `setjmp/longjmp`; the core also raises Pascal exceptions. | Preserve protected errors, do not stub `lua_pcall` or error recovery. Align FPC/C exception mode and validate a Lua→Pascal callback→Lua error round trip, clean recovery and subsequent successful commands. |
| DRL `src/drl.inc` requests `m` outside Windows; original native paths use file/config/WAD/profile IO and a blocking game loop. | Resolve math/runtime imports with the chosen WASI linker. Supply explicit virtual-file/storage/clock services and an original-language command-step seam or a proven worker host. Do not replace command/combat rules merely to avoid the blocking loop. |

[SDK 34's official setjmp/longjmp documentation](https://raw.githubusercontent.com/WebAssembly/wasi-sdk/wasi-sdk-34/SetjmpLongjmp.md) supplies a concrete mechanism: C compilation/link uses `-mllvm -wasm-enable-sjlj -lsetjmp -mllvm -wasm-use-legacy-eh=false` for standard WASM exception instructions, or explicitly chooses legacy instructions with `true`. With LTO the LLVM flags also reach the linker. This support remains under active development. Select the matching FPC exception mode from the exact acquired compiler's help/source and verify browser support; no unverified FPC exception flag is prescribed here.

[LLD's official WASM documentation](https://lld.llvm.org/WebAssembly.html) warns that mismatched signatures may otherwise become trapping stubs plus warnings. Use **`--fatal-warnings`**, explicit exports and audited imports for the mixed-core probe. Dynamic linking is experimental; static mixed-core linkage is the first candidate. An Emscripten C object/runtime is not automatically a WASI object/runtime, even though both contain WASM. Do not mix their libc/system interfaces without a separate compatibility proof.

## Browser boundary and next measurable steps

FPC's [official WASM/browser tutorial](https://www.freepascal.org/~michael/articles/fpcwasm1/fpcwasm1.pdf) demonstrates a browser WASI host and custom imports. It does not make a native blocking `_start` into a browser-friendly turn API. Pas2JS can host the module; it is not selected as a transparent rewrite of a core that relies on pointers and Lua C callbacks. This is an architectural inference from the actual source dependencies, not a tested failure of every possible transpiler route.

1. Pin and inspect a task-local official compiler; record headers, archive SHA-256, source revision, notices, self-report and target/RTL availability. Complete an authored Pascal wasip1 hello-world/explicit export browser probe. If absent, build the cross compiler/RTL from pinned official source with recorded bootstrap/make.
2. Acquire/hash a matched WASI C SDK or validate installed Clang plus pinned sysroot/runtime. Compile one authored scalar C function called by Pascal, then a callback/userdata round trip; inspect imports/exports and enforce fatal linker warnings.
3. Adapt only Lua binding/configuration/platform seams in a separate tree. Prove integer/record layouts, heap ownership, protected errors and mixed exception behavior. Preserve the original runtime and rule sources.
4. Load original Lua scripts, construct original state/generate a level and execute original commands using a thin Pascal facade. Compare fixed-seed traces and failure behavior against source/native references. Core-owned alloc/free plus byte-buffer init/command/snapshot/save/load functions are proposed ABI operations, **not implemented exports**.
5. Finish semantic IDs at the original text-producing Pascal/Lua seams, use English/Japanese JSON in Rust display, and preserve core serialization through versioned browser storage. Run complete original-game desktop/mobile flows and the full feature/text/license gates before publication.

At this checkpoint neither a DRL original-core WASM build nor the mixed Pascal/Lua browser ABI is verified. The missing compiler/ABI evidence is a concrete next gate. Official support and runtime mechanisms justify a reproducible investigation; they do not establish incompatibility or completion.
